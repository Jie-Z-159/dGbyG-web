Server Limits & Usage Guidelines

Rate Limits

To ensure fair usage and server stability, the following rate limits are enforced:

Endpoint Limit Window
Search GEMs (/gem-dg) 300 requests 1 hour
Single Prediction (/calculate) 500 requests 1 hour
Batch Prediction (/batch_calculate) 100 requests 1 hour
API Endpoints (/api/*) 300 requests 1 hour
Note: Rate limit information is included in API response headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset

Batch Processing Limits

For batch calculations, the following limits apply:

  • Maximum batch size: 500 reactions per request
  • Processing time: Typically 1-3 seconds per reaction
  • Job retention: Results are stored for 3 days
  • Result access: Use Job ID to track progress, Result ID to retrieve results
Tip: Batch jobs run asynchronously. You'll receive a Job ID immediately to track progress.

Result Persistence

Search results and batch jobs are temporarily stored:

  • Batch jobs: Job ID and Result ID are valid for 3 days
  • Job tracking: Use Job ID to check progress via "Job Progress" button
  • Result retrieval: Use Result ID to view results via "View Result" button
Important: Save your Job ID and Result ID - they remain valid for 3 days.

Timeout Limits

  • Single calculation: 30 seconds maximum
  • Batch calculation: 5 minutes maximum
  • Search queries: 30 seconds maximum

Best Practices

  1. Use batch endpoints for multiple calculations instead of repeated single requests
  2. Monitor rate limit headers to avoid hitting limits
  3. Save result URLs for future reference (valid for 24 hours)
  4. For very large datasets, consider downloading model data and running locally
  5. Use the job status endpoint to track long-running batch calculations
Need higher limits for research purposes? Contact us to discuss your requirements.
